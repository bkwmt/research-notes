3. MDOH_Project

目的

README 描述 MDOH 為「發展方法論與技術工作流程，主動運用口述歷史典藏的口語、聽覺與聲音面向」，涵蓋回溯數位化與原生數位材料；目前焦點是以 AI 工具結合非數位方法偵測訪談中的笑聲，理由是笑聲、遲疑、語速等聲音元素常被人工逐字稿省略。 來源：https://raw.githubusercontent.com/International-Digital-Oral-History-Lab/MDOH_Project/main/README.md

笑聲偵測與多模態對齊使用什麼技術

儲存庫未載明。沒有任何程式碼、模型名稱或資料。idohl.org 的 MDOH 頁面只提到語音轉文字管線使用 WhisperX，多模態分析在逐字稿之後進行，涵蓋逐字稿、聲音、波形、頻譜圖與中繼資料；笑聲偵測採用哪個音訊模型（例如 openSMILE 或深度學習分類器）網站與儲存庫均未說明。理論基礎是 Smyth, Nyhan & Flinn (2023) Digital Scholarship in the Humanities 38(2): 720–736 的多模態口述歷史論文。 來源：https://idohl.org/MDOH/ ；https://doi.org/10.1093/llc/fqac094

可借用之處

只有概念層可以借用：把「逐字稿省略的副語言事件」（笑聲、遲疑、停頓）當成分析類別而非雜訊。這與 extract_ohistory 把「證詞的多重樣貌是證據層次、不是待清理的雜訊」的立場相容。我們的 SRT 帶有時間碼，若日後要把音訊層的事件掛回句層，MDOH 這條線是可對照的對象，但目前對方沒有任何可比的實作。

與 extract_ohistory 的差異

  • 對方以音訊為主要對象、尚無釋出；我們以文字為主，音訊未進管線。
  • 對方沒有任何程式碼或資料釋出，無法比對出處層、時間碼或共指做法。

5.4.3 抽取流程（依投影片與 Zenodo 摘要）

  • 四層架構：Discourse（訪談作為對話事件）、Narrative（主題連貫的敘事單元）、Claims（具化的斷言，帶講者歸屬與知態立場）、Reference（人物、組織、技術、事件的策展識別碼，掛上 Wikidata Q 編號）。
  • 「分層多代理工作流程」：context stratification → extractor LLMs × 3 configs → consolidator → output validation → validated schema，再加 human-in-the-loop（評估、結構感知分群、修訂綱要）。
  • 三趟抽取：Pass 1 open（無綱要）、Pass 2 schema-guided（注入本體）、Pass 3 RQ-driven（針對研究問題的探針）；輸入是切塊（chunks）而非整卷，理由是「context rot」。三趟結果交由 reconcile 與人工 review；「收斂→信心，分歧→綱要的缺口」。
  • 投影片第 7 頁指出通用 LLM 零樣本抽取的三種失效：參數知識覆寫（把 Malloy 從未說過的「educatedAt University of California」產生出來）、把遲疑壓平（Nitti 的「if I remember correctly, for $242,000」丟棄保留語）、context rot（整卷輸入時講者歸屬失敗）。 來源：同上 PDF 第 7、8、9、12 頁；https://zenodo.org/records/22115456

5.7 可借用之處

  1. 知態立場四欄位的設計（claim_type／certainty_level／temporal_grounding／attribution_type＋is_negated）是一組可直接參照的受控詞表，特別是 attribution_type 把 direct_quote、indirect_report、general_attribution 分開，對應我們的「來歷」（自述／他述／消息來源交代）。但要注意：對方這四欄是由模型判定的，我們的紅線是來歷由程式掃描線索詞，可以借用詞表、不借用做法。
  2. 「三趟抽取、設計成會分歧」（open／schema-guided／RQ-driven）與「收斂→信心、分歧→綱要缺口」：把多組態一致性當信心訊號，與我們斷句線的「共識／減票共識／單次支持」證據等級同構，可引為文獻支持。對方多了一層：把分歧當成本體該修的證據，而不只是當雜訊。
  3. medorah:Divergence（投影片第 11 頁）：把兩位講述者對同一事實的不同說法（TEI 在 MLA 還是 Vassar College 開始）建成一個一級物件，兩筆宣稱都保留、由歷史學者標記 divergenceType 而不裁決。這對我們「跨訪談合併人物」時遇到的矛盾證詞是現成的表徵方案。
  4. 單卷 160 個自由型別、436 個關係標籤這組數字，是「讓模型自由命名會發生什麼」的量化證據，可用來支持我們「分類交給演算法、模型只圈字」的設計。
  5. 「over-specified」這個錯誤類別（8.5%）：證據說的是「擁有」而模型寫成「使用」。我們的 ORSE 線衡量「跨距是否含動詞」時，可以多一個「跨距動詞與邊標籤強度是否一致」的檢查。
  6. generate_report_modern.py 的結構模式統計（主詞型別→關係→受詞型別、基數、定義域／值域多樣性）是純程式、幾十行可重寫，與我們 orse_label_exp.py 的歸納動詞表互補。

6.4 本體內容（三個 Turtle 檔）

6.4.1 內容層：Ontology/Ontology Prototype V0.2.ttl

  • 格式 OWL／Turtle；命名空間 http://example.org/medorah/（佔位用途的 example.org，非持久 URI）；dcterms:created "2026-05-07"、owl:versionInfo "0.2"。
  • 43 個具名類別（grep owl:Class 得 47，其中 4 個是 owl:unionOf 匿名類別）：根 Entity，7 個頂層 Actor、Event、Artefact、ConceptualItem、SpatialEntity、TemporalEntity、Property，其下 Person／Organisation／Group、Project／CourseAndProgramme／Conference／EventSeries／Activity、Technology（Software／Hardware／Standard／Infrastructure）、Work（InformationResource／Publication／Corpus／Database／Dataset／Website）、ConceptualFramework（Theory／Paradigm／SchoolOfThought／Definition）、Methodology（Method／Practice／Technique）、Discipline（AcademicDiscipline／FieldOfStudy／ResearchArea）、RoleOrPosition／Qualification。
  • 51 個物件屬性，組織成 11 種關係模式，每種一個上位屬性加子屬性：Actor→Actor hasSocioInstitutionalRelationWith（12 子屬性：hasEmploymentAt、studiedAt、founded、collaboratedWith、mentorsOrSupervises、providesResource、influences、hasEducationIn、chairOf、represents、affiliatedWith、mergedWith）；Actor→Artefact createsItem／createdBy（authorsWork、publishesWork、createsArtefact、developsTech）；uses／usedBy（usesTechnology、usesCorpusOrResource）；Actor→ConceptualItem engagesWithConcept（workInField、studiesField、coinsOrDefinesTerm）；Actor→Event engagesIn／isEngagedInBy（participatesIn、organises、presentedAt、funds）；Actor→Property hasProperty／isPropertyOf（hasRoleOrPosition、hasQualification）；Event→Spatial|Organisation takesPlaceAt；Event→Temporal hasTimeExtent；Entity→Entity dependency（isPartOf、conceptuallyInfluences、runsOn）；Artefact→ConceptualItem about（hasTopic、implementsConcept）；Actor→Spatial hasResidence（residesIn、grewUpIn、workedIn、locatedIn）。collaboratedWith 與 mergedWith 宣告為 owl:SymmetricProperty。
  • 1 個資料屬性 hasAttribute（Entity→rdfs:Literal，萬用欄）。
  • CIDOC-CRM 對齊：只有非正式對應，沒有任何 owl:equivalentClass、rdfs:subClassOf crm:* 或 P 屬性對映。 以 skos:scopeNote 註記「Plausibly alignable with ... no formal equivalence is asserted in this prototype」：Person↔E21 Person、Organisation↔E74 Group、Event↔E5 Event、SpatialEntity↔E53 Place、TemporalEntity↔E52 Time-Span；Work／Publication↔schema:CreativeWork、dcterms:BibliographicResource、IFLA-LRM／FRBRoo。設計文件第 7 節同樣記載「No formal alignment is committed in v0.2」。
  • 沒有 Statement、Claim、Evidence、Speaker 之類的類別。 本體的 rdfs:comment 明確說明：這是「entity-centric Fabula／Reference layer：受訪者談論的對象，而非敘事結構、立場或知態情態。宣稱、出處、信心與證據跨距應在 Claim 層、RDF-star 標注、具化陳述節點或互補的 SHACL／PROV-O 模型中建模」。亦即投影片裡的 Claims 層與 medorah:Divergence 類別不在已釋出的 TTL 裡。
  • 時間表徵：TemporalEntity 是一個實體類別（「年、十年、時期、日期範圍」），只透過 hasTimeExtent（Event→TemporalEntity）掛在事件上；沒有 xsd:date／gYear 資料屬性，沒有區間起訖，沒有相對時間或不確定時間的表徵。
  • 與投影片的差異：投影片稱「22 classes（7 top-level + 15 sub）」，TTL 有 43 個具名類別。差異原因未載明，可能是投影片計算的是另一個版本。 來源：https://raw.githubusercontent.com/articoder/MeDoraH_Ontology/main/Ontology/Ontology%20Prototype%20V0.2.ttl ；https://raw.githubusercontent.com/articoder/MeDoraH_Ontology/main/documentation/Ontology/MeDoraH%20Ontology%20Prototype%20v0.2.md

6.4.2 檔案層：MeDoraH Ontology - File.ttl

  • 命名空間 http://www.medorah.org/ontology#（與內容層不同）。8 個自訂類別 Interview、Interviewer、Interviewee、Project、Collection、AudioFile、TranscriptFile、SpeechSegment，另宣告外部類別 foaf:Person、dcterms:BibliographicResource、prov:Entity。Interview 是 dcterms:BibliographicResource 與 prov:Entity 的子類；Interviewer／Interviewee 是 foaf:Person 的子類。
  • 10 個物件屬性（hasInterviewer、hasInterviewee、partOfProject、inCollection、hasAudioFile、hasTranscriptFile、hasSpeechSegment、speaker、audioFileReference、wasGeneratedBy）加 prov:wasGeneratedBy；38 個資料屬性。
  • 時間碼在這一層：SpeechSegment 有 startTime／endTime（xsd:time）、transcriptText、speaker（→foaf:Person）、audioFileReference、segmentIndex、synopsis、keywords、speechCharacteristics。但 5.5 節的抽取 JSON 完全沒有用到這一層，兩層之間沒有連結屬性。 來源：https://raw.githubusercontent.com/articoder/MeDoraH_Ontology/main/MeDoraH%20Ontology%20-%20File.ttl

6.4.3 中繼資料詞彙：Metadata Vocabulary/OH_metadata_vocab_V3.ttl

  • 標題「MeDoraH Oral History Metadata Vocabulary」3.0 版，命名空間 http://hiddenhistories.net/oral_history_ontology/，建立 2024-07-01、修改 2026-03-08；基於 Oral History Association Metadata Task Force 的「Metadata Elements for Oral History 1.1」。8 個類別：Oral_History_Life_Cycle 與四個階段子類 PlanStage、InterviewStage、ProcessingStage、PublicationAccessStage，加 Person、Interviewer、Interviewee；2 個物件屬性、27 個資料屬性（interviewDate、recordingDuration、transcriber、translator、processingTools、rights、orcid、viafID 等），對映到 dc:／dcterms: 詞彙。V2→V3 的差異是屬性改名與增刪（例如 transcriberName→transcriber，新增 citation、rights、publisher、summary）。
  • 這份詞彙對應 Humbel, Vlachidis, Zhang, Schmidt, Prishchepova, Nyhan & Flinn (2026)〈Implementing FAIR principles for interoperable oral history collections through mappings to Dublin Core〉，MTSR 2025（2025-12-15 至 19，Thessaloniki），Springer CCIS，in press。UCL Discovery 頁被 Cloudflare 擋住未能讀取全文；搜尋摘要稱其「以 OHA 2022 年標準中立的中繼資料元素彙編為基礎，提出對映到 Dublin Core 的子集綱要」，另有搜尋結果提到該綱要「對齊 CIDOC-CRM、Dublin Core 與 PBCore」，但 TTL 裡只有 dc／dcterms，沒有 CRM 或 PBCore 的對映三元組。 來源：https://raw.githubusercontent.com/articoder/MeDoraH_Ontology/main/Metadata%20Vocabulary/OH_metadata_vocab_V3.ttl ；https://discovery.ucl.ac.uk/id/eprint/10220832/（2026-10-05 回 403／Cloudflare 驗證頁）；https://www.ucl.ac.uk/institute-of-advanced-studies/events/2024/nov/oral-histories-metadata-usability-accessibility-and-interoperability

6.6 設計文件要點（documentation/Ontology/MeDoraH Ontology Prototype v0.2.md）

  • §2.1「Networks of Recollection」：知識圖譜儲存的是「來源中被憶及與表述的連結」，不是客觀史實；關係解釋為「以來源為根據的宣稱」，出處與信心在管線／KG 層處理（RDF-star 或陳述節點）；矛盾說法並存，「真值維護是研究活動，不是本體要求」。
  • §9.1「KG Population and Provenance」：每筆抽取關係應附來源（訪談、逐字稿、段落 id）、證據跨距（引文或位移）、抽取器中繼資料（方法／模型／提示版本）、信心與驗證狀態（自動＋人工審查）。這是規範性要求，釋出的資料裡只有前兩項（句 id 與證據句），模型與提示版本沒有落在任何公開檔案。
  • §8 能力問題（competency questions）列了四組，但儲存庫沒有對應的 SPARQL 查詢或測試。
  • §10.3 開放問題：studiedAt vs hasEducationIn 是否都要；事件地點能否是機構；人對人的 influences 與概念對概念的 conceptuallyInfluences 要在提示詞裡分清楚。 來源：https://raw.githubusercontent.com/articoder/MeDoraH_Ontology/main/documentation/Ontology/MeDoraH%20Ontology%20Prototype%20v0.2.md

6.7 可借用之處

  1. 「11 種關係模式、每種一個上位屬性、子屬性逐步特化」的做法對應我們 life_nodes.py 六類動詞表：對方的 §9.2 明寫「先抽取到 hasSocioInstitutionalRelationWith，證據累積後再細化成 studiedAt」。我們 ORSE 線的述詞歸納可以採用同樣的兩層結構，粗層保證召回、細層依靠動詞表。
  2. Fabula／Reference 層與 Claim 層分開的架構決定，與我們 2026-09-10 架構審查提出的 Speaker -> Claim -> Event -> participants 三層同向；對方把「誰說的、多確定、什麼時候的記憶」全部歸入 Claim 層，實體層保持乾淨，可直接引為設計先例。
  3. 檔案層的 SpeechSegment（startTime／endTime／speaker／audioFileReference）是我們 SRT 時間碼最自然的 RDF 落點；若日後要輸出 RDF，這一層可直接沿用詞彙，但要補上與內容層的連結屬性（對方沒有）。
  4. TemporalEntity 當實體而非字面值，讓「1970 年代」「戰後」這種模糊時間可以成為節點；我們的 time_anchor.py 可信層 A–F 若要納入圖中，這是可對照的表徵。
  5. 中繼資料詞彙對映 OHA 1.1 與 Dublin Core 的做法，對我們日後描述 314 個 SRT 與北流人物頁的來源層有參考價值。

6.8 與 extract_ohistory 的差異

  • 對方的本體是人設計的綱要，抽取第二趟直接注入；依我們紅線第 5 條，這整條線屬「含人工標注」。我們的零標注線沒有對應物。
  • 對方沒有 Claim 層的正式本體，宣稱的出處與立場只存在 JSON 欄位，沒有 RDF 表徵；我們目前也沒有 RDF，但邊上的 來歷、年_可信層、跨距重疊端點 是程式化的對應物。
  • 對方 CIDOC-CRM 對齊只到 scopeNote，沒有 P 屬性；若我們要與 NTU-Bonn 的 CIDOC CRM 資料庫銜接，對方的本體幫不上忙。
  • 對方沒有別名、共指或人物登錄簿的表徵（Reference 層依靠 Wikidata Q 編號，投影片稱 35.7% 掛上）；我們 output/registry/ 五個變因的別名合併是對方沒有的。

7. 橫向判斷：這套開源釋出能不能讓別人重跑他們的結果

結論：可以「檢視」結果，不能「重跑」抽取。 分段說明：

  1. 有資料、無核心程式。 19 卷切分逐字稿、1,647 筆抽取結果（Combined.json）、304 筆本體映射示範、366 實體／598 關係的手工編碼網絡都在，但從逐字稿到抽取結果那一段（三趟 LLM 抽取、consolidator、投票驗證、本體映射）全部封在 NarraGraph 的二進位檔裡。沒有原始碼、沒有提示詞、沒有模型與參數紀錄。九個 release tag 指向同一個 commit，證明建置來源不在這個儲存庫。idohl.org 開源頁說 NarraGraph 原始碼「via MeDoraH_NLP repository」與事實不符。
  2. 有程式的部分缺輸入。 分群腳本的輸入 parquet 在作者本機路徑，產生嵌入的 embedding_analyzer 套件不存在；話輪切分程式只在 issue #6 有文字描述。真正能從公開檔案執行到底的只有「抽取 JSON → HTML 儀表板／networkx 網絡圖」這一段（generate_report_modern.py、semantic_triple_analysis.py、兩支前處理腳本），而這段不涉及任何模型。
  3. 無依賴宣告、無授權。 四個儲存庫都沒有 requirements、pyproject 或 LICENSE。沒有 LICENSE 意味任何人重用程式碼或資料在法律上都沒有依據，「開源」一詞在此只成立於「可以檢視」。
  4. 評估不可重現。 91.3% 那組數字來自人工回讀，回讀規程、人數、一致性未公開；沒有 gold standard 檔案；沒有評估腳本。
  5. 文件與實體不符處多。 MDOH README 列出六個資料夾實際零個；MeDoraH_Project README 連結到五個 404 的儲存庫；MeDoraH_NLP README 的 Omeka Front End/ 不在 main；MeDoraH_Ontology README 的 /extensions、/tools 不存在；投影片 22 類 vs TTL 43 類。
  6. 對我們的意義。 這套釋出的價值在資料與表徵設計（知態立場詞表、Claim／Reference 分層、Divergence 物件、兩層關係模式），不在可執行的管線。要引用他們的方法，可引用 NKOS 2026 投影片與 DH2026 摘要；要陳述「他們的程式碼如何處理 X」，除了後處理與分群之外都說不出來。
