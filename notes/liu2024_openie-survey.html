Liu 2024_開放式資訊抽取綜述：從規則式模型到大型語言模型

ACL Anthology 2024.findings-emnlp.560。同儕審查（EMNLP Findings）。西湖大學、羅徹斯特大學、浙江大學、哥倫比亞大學、阿里達摩院、東北大學。
  • 對應待查問題：⑧本體學習與 schema 歸納、①LLM 抽取現況、⑤評估
  • 一句話定位：把開放式資訊抽取（OpenIE）二十年的發展整理成一條線，最有用的是兩組分類——三種任務設定（ORTE／ORSE／ORC）與兩類評分器（token-level／fact-level），前者可以用來替我們兩條並行的抽取線命名，後者直接回答「該用哪種指標」。

1. 貢獻

一份綜述。三件事：（一）把 OpenIE 的任務設定分成三類並說明各自的優缺；（二）按時間整理主流方法，分成前神經時代、神經時代、大型語言模型時代；（三）討論 LLM 對這個領域的衝擊，並提出未來方向。

2. 知識怎麼被萃取（抽取流程）

它整理的是「別人怎麼抽」。三種任務設定是全篇對我們最有用的分類：

  • ORTE（Open Relation Triplet Extraction，開放關係三元組抽取）：從文字直接抽出三元組。這是 Banko 等人 2007 年定下的經典設定——從大量非結構化網頁文字自動抽出 (實體1, 關係, 實體2)，其中三個成分都是輸入句裡選出來的詞。論文特別指出：雖然大家慣用「三元組」這個詞，實際抽取任務並不總是限於三元組，也可以涉及更多元的 n-ary 關係，例如條件、時間資訊等。
  • ORSE（Open Relation Span Extraction，開放關係跨距抽取）：先有主詞與受詞，再去找表達關係的那段文字跨距。優點是把個別模型簡化，能處理巢狀關係；缺點是錯誤會逐步傳遞，而且計算成本高。
  • ORC（Open relation clustering，開放關係分群）：把句子與句中不同的主詞受詞配成關係實例，反覆最佳化其表示，收斂後做分群，把各種不同的關係表述聚成同一類。優點是有助泛化；缺點是相似度計算量大、可能失去具體性。

「開放」的意思在三種設定裡都一樣：不限制關係型別。

3. 知識怎麼被組織（結構與屬性）

綜述本身不提出結構。但它整理的資料集建立方式分四類，對我們有參考價值：

  • 問答衍生：把眾包問答資料集轉換而來（OIE2016、CaRB、LSOIE 等）。
  • 眾包標注：直接人工標注（WiRe57、SAOKE、BenchIE）。
  • 知識庫衍生：把知識庫的三元組與語料文字對齊——這就是 Mintz 那條遠距監督的路（NYT-FB、TACRED、FewRel、T-REx）。論文指出知識庫衍生的資料集多半用於 ORC 設定。
  • 指令式：把抽取任務改寫成指令跟隨任務，以利用 LLM 的能力。

4. 表示法：是不是三元組？

綜述涵蓋的主流是三元組，但它明確承認 n-ary 關係（含條件、時間）也在範圍內。它沒有討論出處、時間欄位或信心分數——這再次說明出處在這個研究社群裡不是議題。

6. 評估

這是本篇對我們最直接有用的一節。 評分器分兩類：

  • token-level scorers（詞元層評分器）：關注個別詞元，確保精確度與語意準確，容許語言上的變異、提升簡潔性、能適應 LLM 那類複雜輸出。
  • fact-level scorers（事實層評分器）：評估抽取對資訊的忠實度，驗證語意與資訊的完整性，目的是確保知識抽取可靠。BenchIE 屬於這一類。

論文給出的配對原則寫得很清楚：

從任務形式的角度看，token-level 評分器較適合 ORSE（輸出簡潔）與 ORTE 裡的標記式模型（輸出是從輸入衍生的精確詞元）；反之，fact-level 評分器較適合 ORTE 裡的生成式模型，特別是 LLM，因為它們的輸出多樣、需要語意層的評估。

在 ORC 設定下用的是分群指標：B³、V-measure、ARI。

7. 發現的問題與限制

論文自己的判斷（6.2 節）：LLM 在經典指標（尤其 token-level）上常常拿到最好的成績，甚至零樣本就達到當時最佳；但它們在長尾與更困難的任務上表現不佳，而且幻覺是相對於序列標記那類前 LLM 方法的主要劣勢，使得忠實度與可靠性成為重要疑慮。

它提出一個值得思考的判斷：LLM 讓標準 IE 與 OpenIE 的界線變模糊。兩者現在都在同一個任務設定下處理，差別只在 schema 設計——標準 IE 的 schema 對關係與實體的限制更多。他們謹慎地說 OpenIE 未來可能被視為 IE 裡一個更複雜困難的情境，而不是獨立的分支。

未來方向裡有三點與我們相關：

  1. 資料集仍然小而窄，需要更多語言、領域與來源。
  2. 需要能評估 LLM 式輸出的新指標——「忠實度這類面向仍然嚴重依賴人工評估，缺乏公認的指標」。
  3. 多語言是明顯的缺口：「多語言至關重要，但多語言能力有明顯落差⋯⋯尤其缺乏用 LLM 處理這些挑戰的努力」。他們自己也只涵蓋中文，多語言模型放在附錄簡述。

我讀出來的：綜述對「零樣本 LLM 達到最佳成績」的說法，與 Papaluca 2024 實測的「零樣本 F1 近乎 0」看似矛盾。兩者其實不衝突——差別在評分器：綜述講的是 token-level 指標下的成績，Papaluca 用的是要求對應封閉關係集的嚴格比對。這正好印證綜述自己的分類：評分器選錯，結論就會反過來。

8. 對 extract_ohistory 的啟示

（一）我們兩條抽取線各有現成的名字，而且第三種設定我們還沒試。

  • triple_free_exp.py（不限動詞、模型自判、結構化輸出）＝ ORTE 的生成式版本。
  • triple_exp.py（程式用 life_nodes.py 界定述詞、模型只圈原文的字）＝ 介於 ORTE 的標記式版本與 ORSE 之間；因為模型輸出的是輸入裡的精確詞元，性質上是標記式的。
  • ORSE 我們沒試過：先確定主詞與受詞（例如先用主角線定人物），再讓模型只找「表達關係的那段字」。這其實跟 DialogRE 的觸發詞標注是同一件事。值得當一個具名變因加進來，因為口述歷史的人名相對好認（人名 NER 有 65.9%，作品名只有 1.1%），先定人物再找關係可能比一次抽三個成分穩。它的已知缺點是錯誤傳遞——人物定錯，關係就跟著錯，這要在報告裡說明。
  • ORC 就是動詞表歸納：把各種關係表述聚成同一類。AutoSchemaKG 的概念化屬於這一類，我們若要從語料長出動詞表，做的就是 ORC。

用這三個名字替我們的變因命名，好處是報告寫出來能對上這個社群的詞彙，不必自創說法。

（二）評分器怎麼選，有現成的答案。

論文的配對原則直接回答了我在讀 BenchIE 時提出的問題：

  • triple_exp.py 的輸出是輸入裡的精確詞元（模型只圈字、程式逐字驗證），所以可以用 token-level 評分器。
  • triple_free_exp.py 是生成式輸出，必須用 fact-level 評分器（BenchIE 那一路）。

這比我先前在 _卡點對照表.md 寫的「絕不能用字詞重疊計分」更準確。正確的說法是：兩條線要用不同的評分器，而且不能拿它們的分數直接互比。這一點如果搞錯，會得到「程式界定動詞那條線表現比較好」的假結論——那只是因為它被用寬鬆的指標評。

（三）中文的可用參照點只有三個，而且都不是口語。

SAOKE、BenchIE-zh、COER。BenchIE-zh 是翻譯來的（見 gashteovski2022_benchie.md），SAOKE 與 COER 是百度百科與中文新聞。沒有一個是口語，也沒有一個是繁體。 這替本專案的定位再加一筆證據：繁中口語逐字稿在 OpenIE 這條線上是空白。

COER 有一點值得留意：100 萬條、由非監督抽取器自動建立。若我們要找一個「中文的、大規模的、不靠人工標注的」參照點，它是目前唯一的候選——但它的領域（百科與新聞）與我們差太遠，只能當方法上的先例，不能當效能對照。

（四）三元組不是唯一選項，這是社群自己說的。

論文在定義 ORTE 時明講「實際抽取任務並不總是限於三元組，也可以涉及更多元的 n-ary 關係，例如條件、時間資訊」。這句可以直接引用來支持我們不走純三元組——不是標新立異，是這個領域自己承認的範圍。

（五）忠實度沒有公認指標，這是空地也是麻煩。

「忠實度這類面向仍然嚴重依賴人工評估，缺乏公認的指標」——這既說明我們沒有現成的尺可以用，也說明若我們設計出一套程式化的忠實度檢查（出處落地、逐字驗證、跨人佐證），那本身就是可以報告的方法貢獻。

該避免的

  • 不要引用「零樣本 LLM 達到最佳成績」而不註明評分器。 那是 token-level 下的結論，換成 fact-level 就反過來（Papaluca 的表 4）。
  • 不要把 LLM 時代的樂觀敘事照搬。 綜述自己也說 LLM 在長尾任務上不行、幻覺是主要劣勢，而口述歷史裡的人物與事件恰恰全是長尾。

與四條紅線的相容性：綜述不做實驗，沒有直接的相容性問題。但它整理的主流方法裡，出處、時間、信心欄位全部缺席，這再次支持「出處設計沒有現成模板」的判斷。
