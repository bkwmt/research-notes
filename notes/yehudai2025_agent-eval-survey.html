Yehudai 2025_LLM agent 評估綜述

  • 完整書目：Yehudai, A., Eden, L., Li, A., Uziel, G., Zhao, Y., Bar-Haim, R., Cohan, A., & Shmueli-Scheuer, M. (2025). A Survey on Evaluation of LLM-based Agents. arXiv:2503.16416（v2, 2026-04-23）. 預印本，未經同儕審查。作者群來自希伯來大學、IBM Research、Yale。
  • 對應待查問題：③harness／agent 評估、⑤無 gold standard 評估
  • 一句話定位：這是第一篇系統整理「怎麼評估 LLM agent」的綜述。它把 agent 評估拆成五個視角，並在結尾明確點出「把 LLM 本身和它的 harness（鷹架）拆開來評估」是一個尚未解決、才剛起步的方向。對本專案而言，它是學術端最接近「harness engineering」概念的文獻，可用來替本專案的定位背書。

1. 貢獻

這篇自稱是「第一份」全面盤點 LLM agent 評估方法的綜述（survey）。它不提新方法、不做新實驗，貢獻在於把散落各處的 benchmark（評測基準，指一組固定的任務加標準答案，用來打分比較不同系統）和評估工具整理成一張地圖，並點出還沒被解決的缺口。

它把整個領域切成五個視角：（1）agent 的核心能力（規劃、工具呼叫、自我反思、記憶）；（2）特定應用領域的 benchmark（網頁、軟體工程、科學、對話 agent）；（3）通用型（generalist）agent 的評估；（4）跨 benchmark 的共通維度分析；（5）給開發者用的評估框架與工具。它同時維護一個持續更新的 GitHub 清單，因為這個領域變動太快，論文本身只是某個時間點的快照。

對人文學者要抓的重點是：這篇的價值不在任何單一技術，而在它替「agent 該怎麼被評估」畫出了討論的座標，並老實承認多數現行做法都還很粗糙。

2. 知識怎麼被萃取（抽取流程）

這篇不是抽取知識的論文，沒有抽取流程可談。它的「輸入」是文獻本身，「輸出」是分類與判斷。這一節在本專案的關注點裡對應到的，其實是它怎麼描述「agent 執行任務」這件事，因為本專案的 srt-extract 也是一個多步驟的 agent 流程。

值得記下的是它反覆強調的一個區分：agent 的表現同時來自兩個東西，一個是背後的 LLM（backbone），一個是 agent harness（鷹架，指包在模型外面、負責規劃、呼叫工具、管理記憶與串接多步驟的那層設計）。這正是本專案用 Agent Skills 做的事。這篇把這兩者混在一起評估視為當前 benchmark 的通病（見第 7 節）。

3. 知識怎麼被組織（結構與屬性）

論文的組織主軸是第 5 節提出的「核心 benchmark 維度」，它用五個彼此獨立的維度來描述任何一個 agent benchmark（見它的 Table 1）：

  • 資料策劃（Data Curation）：純人工、純合成、還是混合。它指出高品質 benchmark 幾乎都用混合策略，並點出一個張力：人工標註能保證資料正確，但無法規模化，因此需要「能自動化又不犧牲品質」的方法。
  • 環境（Environment）：靜態（static，離線紀錄或快取，agent 的動作不改變狀態）對比動態（dynamic，像 Docker 容器或瀏覽器沙盒，動作會改變後續狀態）。它明確批評靜態環境「無法捕捉錯誤的連鎖效應」，一步錯不會影響後面，因此看不出長程任務的失敗模式。
  • 互動介面（Interaction Interface）：程式碼與終端機、工具呼叫（schema 綁定的函式）、圖形介面三類。
  • 指標（Metric）：最普遍的是任務完成率，但實作方式各異（單元測試、狀態比對 state matching、答案比對 answer matching、端到端等）。
  • 安全與穩健性（Safety and Robustness）：多數 benchmark 沒有，它視為重大缺口。

第 6 節則把「評估框架」（給開發者的工具，如 LangSmith、Langfuse、Galileo 等）按評估粒度組織成三層：最終回應評估（final response）、逐步評估（stepwise，逐一檢查每個動作、工具呼叫、路由決策）、軌跡評估（trajectory，看 agent 整條走到完成的路徑）。這個「粗到細」的分層對本專案的 QA 設計有直接參考價值。

4. 表示法：是不是三元組？

不適用。這篇不建構知識、不用任何知識表示法（沒有三元組、沒有屬性圖、沒有事件框架）。它評估的對象是 agent 的行為與產出，不是結構化知識。

但它談的「軌跡」（trajectory，agent 為完成任務走過的一連串動作與觀察）在概念上和本專案「每筆知識附出處、推理過程可追溯」有呼應：兩者都關心「不只看最後結果，要看中間怎麼走的」。它對軌跡評估分成兩路（見第 6 節）：

  • 參照式（Reference-Based）：把 agent 走的路徑和一條「理想最佳路徑」比對。論文直言這種做法「本質上受限，因為通常存在多條有效路徑，而且要人工指定參照路徑往往不可行」。
  • 無參照式（Reference-Free）：不預設黃金路徑，改用 LLM 當評審，直接就觀察到的序列評估連貫性、效率、目標導向性等性質。

這一組對比是全篇對本專案「無 gold standard 評估」最直接的支撐，下面第 6、8 節細談。

5. 資料集

這篇不提出新資料集。它盤點的 benchmark 幾乎全是英文、且集中在幾個工程化的領域：網頁操作（WebShop、Mind2Web、WebArena）、軟體工程（SWE-bench 系列、SWE-Lancer、Terminal-Bench）、科學研究（ScienceAgentBench、PaperBench、CORE-Bench）、對話（τ-Bench、τ²-Bench）、通用型（GAIA、AgentBench、HAL）。

要特別記給本專案的一點：完全沒有歷史文本、口述訪談、人文領域的 agent benchmark。它涵蓋的口語／對話只有「任務導向對話系統」那種（訂機票、客服），評估的是能不能用工具把任務辦成，不是能不能忠實理解與結構化一段人的口述。也沒有中文語料的著墨。這個缺席本身就是本專案定位的證據：學術端的 agent 評估還沒碰過人文史料這一塊。

6. 評估

這篇整篇就是在談評估，重點整理如下：

gold standard 的地位正在鬆動。 論文明白指出，完全依賴人工標註的評估「造成嚴重的規模化難題，耗費資源、且產出的 benchmark 在這個快速變動的領域很快過時」。它提出的兩條出路都繞開人工黃金答案：一是合成資料生成（synthetic data generation），二是用 LLM 或 agent 當評審（LLM/agent-as-a-Judge）。它引 Zhuge et al. (2024) 說這不只省下人工標註成本，還「有潛力捕捉 agent 表現中更細緻的面向」。

LLM-as-a-judge 有明確討論，而且是被當成主要趨勢在談。 出現在三處：（a）第 6 節的無參照式軌跡評估與最終回應評估，多數框架用 LLM 評審依預定準則打分；（b）它點出 LLM 評審的核心取捨——通用型評審覆蓋廣但精度低，任務專用評審精度高但範圍窄；（c）第 7 節把「用 LLM 當評審以減少人工標註依賴」列為未來方向。要注意它也順帶點出一個成本問題：當要跑大量軌跡時，昂貴的 LLM 評審本身的成本被現行框架忽略了。

評估設計的自我批評。 論文承認當前 benchmark 大量依賴「粗粒度、端到端的成功率」，這種二元的結果指標「不足以理解 agent 的中間進展」，看不出是工具選錯、還是推理出錯。它呼籲發展細粒度、逐步、針對軌跡的指標。Galileo 的 action advancement metric（動作推進指標，衡量每一步是否真的朝使用者目標前進）被舉為往這個方向走的例子。

它沒有落入「用 LLM 驗證 LLM 的循環」而不自知的陷阱——反而是主動把 LLM-as-a-judge 的精度限制、成本與可靠性攤開來講。這點在方法論上比多數單一系統論文誠實。

7. 發現的問題與限制

論文自己承認的限制（Limitations 節）：領域變動太快，本文只是快照；benchmark 與框架的選取有取捨、可能漏掉小眾方法；涵蓋面廣導致每個對象的分析深度有限；「未來方向」與「關鍵缺口」的判斷帶有預測成分，會隨時間改變。

它在第 7 節整理出的、我認為對本專案最相關的缺口：

  1. 粗粒度指標的問題：只看成功率，診斷不出 agent 哪裡出錯。
  2. 成本與效率被忽略：現行評估重能力、輕成本（token、API 費用、推理時間），這會反向鼓勵造出「很強但很耗資源」的 agent。
  3. 規模化與自動化的張力：人工標註品質高但不可規模化，合成生成可規模化但品質存疑。
  4. 安全與合規幾乎沒人測。
  5. LLM 與 harness 沒有被拆開評估（見下）。

我讀出、它沒明講的疑點：這篇雖然反覆講「harness／scaffold」很重要、該被單獨評估，但它自己盤點的 benchmark 幾乎沒有一個真的做到把 harness 當變因來控制的。它舉 Harbor、Exgentic、Cube 這些「才剛開始」的工作為例，等於承認這個方向目前只有零星嘗試、還沒有成熟的評估協定。換句話說，它把「harness 評估」定位成一個被指認出來、但尚未被填滿的缺口，而不是一套可直接照抄的方法。

8. 對 extract_ohistory 的啟示

這篇最重要的用途，是替本專案的學術定位背書。 它在第 7.2 節「解耦 LLM 與 harness 評估」（Decoupling LLM & Harness Evaluation）明講：目前多數 agent benchmark 把兩個不同的評估對象混為一談——一個是背後 LLM 的固有能力，一個是 agent harness（作者括號註明 a.k.a. scaffold）的設計；把兩者拆開「對於能系統性歸因效能來源是必要的」，並說 Harbor、Exgentic 這類工作「才剛開始（begin to address this）」處理它。這句話幾乎就是本專案處境的學術翻譯：用 skills 精心設計 harness 來做抽取，這件事在學術端連怎麼評估都還沒定案，遑論有人拿它來做人文史料。 本專案因此不是在追一個成熟賽道，而是站在一個學界自己都承認才起步的缺口上。第 5、6 節整理的「沒有歷史／口述／中文 benchmark」進一步坐實這個定位。

可借用的做法：

  • 無 gold standard 的評估路線是被學術認可的，不是本專案的權宜之計。 論文把「參照式評估本質受限、多條有效路徑存在、人工參照不可行」講得很清楚，並把無參照式（LLM-as-a-judge、程式化檢查）當成正當出路。這直接支持本專案紅線一（拒絕配對式 gold standard）與「事件、關係層沒有 gold standard」的設計選擇。
  • 評估分層（最終回應／逐步／軌跡）可搬進 extract-qa。 本專案目前的 QA（出處存在性、年份合理性、腦補檢查）比較偏「最終回應」層，可以再補上「逐步」與「軌跡」視角，例如檢查每一段抽取的判準是否被一致套用、整份抽取的推理路徑是否可追溯。這和本專案紅線四（推理過程落檔）天然契合。
  • 它對 provenance／出處的態度是間接支持。 論文反覆強調二元成功率「看不出中間進展」、呼籲細粒度、可追溯的評估。本專案「每筆知識強制附出處」正是把可追溯性做進資料結構本身，比它盤點的多數 benchmark 走得更前面。
  • Galileo 的 action advancement metric（每一步是否朝目標推進）值得參考，可轉譯成「每筆抽取是否真的貢獻了新的、有出處的知識」這類逐步判準。

該避免、需警惕的：

  • 論文主推 LLM-as-a-judge，但本專案紅線二（絕不叫 LLM 自評信心分數）與之有張力。這裡要區分清楚：本專案反對的是「叫 LLM 對自己的抽取打信心分」，不反對「用另一個 LLM 依明確準則做外部查核」。extract-qa 用 LLM 查核是可接受的，但信心分數仍應由程式化訊號（出處有效性、格式合規、穩定性、數值合理性、跨人佐證）推導，不能退回讓模型自評。論文自己也點出 LLM 評審精度有限、成本被低估，這反而佐證了本專案不把信心交給 LLM 的謹慎。
  • 這篇是預印本、未經同儕審查，且明說「未來方向」帶預測成分。引用時只把它當「領域地圖與缺口指認」，不要把它對某個具體 benchmark 的褒貶當定論。

與四條紅線的相容性小結： 紅線一（無配對式 gold standard）、三（強制出處）、四（可追溯）與本篇高度相容，且能從中找到學術支撐；紅線二（不讓 LLM 自評信心）與本篇主推的 LLM-as-a-judge 不衝突，但需守住「外部查核可以、自評信心不行」這條界線。
