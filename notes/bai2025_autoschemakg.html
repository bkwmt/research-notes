Bai 2025_AutoSchemaKG：從語料自動長出 schema 的知識圖譜建構

  • 完整書目：Bai, J., Fan, W., Hu, Q., Zong, Q., Li, C., Tsang, H. T., Luo, H., Yim, Y., Huang, H., Zhou, X., Qin, F., Zheng, T., Peng, X., Yao, X., Yang, H., Wu, L., Ji, Y., Zhang, G., Chen, R., & Song, Y. (2025). AutoSchemaKG: Autonomous Knowledge Graph Construction through Dynamic Schema Induction from Web-Scale Corpora. arXiv:2505.23628v3（v3, 2025-08-01）。作者來自香港科技大學、香港中文大學與華為 Theory Lab。預印本，未查得同儕審查狀態。程式碼公開（github.com/HKUST-KnowComp/AutoSchemaKG）。
  • 對應待查問題：⑧本體學習與 schema 歸納（新增類別；兼涉①抽取現況）
  • 一句話定位：不預先給任何 schema，讓模型一邊抽三元組、一邊從語料歸納出型別體系；它最重要的實測結果不是那個 92% 的 schema 對齊率，而是「只用實體只能保住原文 70% 的資訊，加上事件節點就到 90% 以上」——這替本專案「生命過程是事件序列、不是實體屬性表」的立場提供了量化證據。

1. 貢獻

四項。第一，提出一個完全不需預先定義 schema 的知識圖譜建構框架：用大型語言模型同時抽三元組與歸納型別體系。第二，把實體與事件並列為圖的基本節點，並用「概念化」（conceptualization）把個別實例組織成語意類別。第三，實際跑了 5,000 萬份文件，建出 ATLAS 系列知識圖譜（9 億以上節點、59 億條邊）。第四，在多跳問答上超越當時最強基線 12–18%，並宣稱 schema 歸納與人工製作的 schema 有 92%（摘要寫 95%）的語意對齊，零人工介入。

它針對的是一個它稱為「內在悖論」的問題：現有的知識圖譜建構都需要領域專家預先定義 schema，這從根本上限制了規模、適應力與領域涵蓋。

2. 知識怎麼被萃取（抽取流程）

三個階段，三個獨立的話術，同一個模型（Llama-3-8B-Instruct）。

  • 階段一：實體—實體（話術 PEE）。要模型摘出段落裡所有重要實體與它們之間的關係。話術裡有一句對本專案特別要緊：「Exclude pronouns from being considered as entities」（不要把代名詞當實體）。
  • 階段二：實體—事件（話術 PEV）。要模型分析事件與實體之間的參與關係。事件的定義是「a single independent sentence」——一個獨立的簡單句子。輸出是 {"Event": "描述某事件的簡單句", "Entity": ["實體1", "實體2", ...]}。
  • 階段三：事件—事件（話術 PVV）。偵測事件之間的關係，型別固定五種：before、after、at the same time、because、as a result（之前、之後、同時、因為、結果）。

輸出一律 JSON，解析失敗會修補（output processing 階段明列 "repair if needed"）。前處理是過濾語言、切段、分批。

Schema 歸納在抽取之後跑。對圖裡的每個元素（事件、實體、關係）叫模型生成至少三個不同抽象層次的概念詞：

  • 事件：「Sam playing with his dog」→「playing」「bonding」「relaxing event」
  • 關係：「participated in」→「engage in」「attend」「involve in」
  • 實體：同樣要抽象型別，但額外餵進鄰居節點的脈絡（取樣最多 Nctx 個鄰居組成脈絡字串）

結果寫成 CSV，把每個節點與每種關係對應到概念集合。

3. 知識怎麼被組織（結構與屬性）

形式定義是 G = (V, E, C, φ, ψ)：V 分成事件節點 VE 與實體節點 VN（兩者不相交），E 是邊（可連實體—實體、實體—事件、事件—事件），C 是概念類別集合，φ 把每個節點對到一組概念，ψ 把每種關係對到一組概念。硬性約束是每個節點與每種關係至少要有一個概念。

所以這是一個三層結構：實例層（實體與事件節點）、關係層（邊）、概念層（型別）。概念層不是預先寫死的本體，是從實例長出來的。

跨文件的去重、實體合併、衝突解決——論文沒有處理。這是它與 Graphusion、KARMA 那一路的差別：它靠規模取勝，不靠融合。

4. 表示法：是不是三元組？

是三元組，但事件節點的內容是一個自然語言句子，這讓它實質上介於三元組與文字節點之間。一個事件節點「Sam playing with his dog」本身就是一句話，它與其他事件之間用 before／because 這類關係連起來。

沒有出處欄位。 論文說抽出的三元組「與對應文字及中介資料一起序列化成 JSON 檔」，但中介資料是文件層級的，圖裡沒有三元組層的來源指向。

沒有信心分數。 有時間資訊，但是關係型的（before／after／at the same time），不是絕對日期欄位。

5. 資料集

兩類。問答語料：MuSiQue、2WikiQA、HotpotQA（各約 6 千至 1.2 萬個文字塊）。預訓練語料：Dolma 1.7 的三個子集——英文維基百科與 Wikibooks（ATLAS-Wiki）、Semantic Scholar 論文摘要（ATLAS-Pes2o）、3% 的 Common Crawl（ATLAS-CC）。

規模：ATLAS-CC 有 3,504 萬個文字塊、2.41 億實體、6.96 億事件、3,107 萬概念，合計 9.37 億節點、59.58 億條邊。

全部是英文書面文本，沒有中文，沒有口語，沒有訪談。

計算成本：78,400 GPU 小時（80GB GPU，Llama-3-8B-instruct 配 Flash Attention）。

6. 評估

四種評估，其中兩種對本專案有用、一種踩紅線。

（一）三元組正確率——踩紅線第 2 條。 用 DeepSeek-V3 當裁判：給它原文與 Llama-3-8B 抽出的三元組，要它指出哪些是錯抽（假陽性）、哪些是原文有但沒抽到（假陰性），據此算精確率、召回率、F1。結果全部超過 90%（ATLAS-Wiki 的實體—實體 F1 94.09，事件—事件 96.01）。這是用一個大模型評另一個大模型，沒有人工驗證環節，數字不能照單全收。論文自稱這是「嚴謹的計數式評估、不靠主觀評分」，但換一個裁判就是換一套答案，這一點它沒有處理。

（二）資訊保存度——這個設計很好，值得學。 拿原始段落生成五題多選題（用 LLaMA-3-70B 出題），然後比較三種情況下的答題正確率：完全沒有脈絡（下界）、給原始段落（上界）、給知識圖譜資料。結果（表 3）：

語料 下界—上界 只給實體 只給事件 事件＋實體
ATLAS-Wiki（8B） 46.29–99.29 65.08 92.69 93.30
ATLAS-Pes2o（8B） 62.32–98.99 80.00 96.97 97.37
ATLAS-CC（8B） 56.08–97.29 76.78 94.87 96.28

只用實體節點，保住的資訊約七成；加上事件節點，逼近上界。 論文的結論是「事件層三元組比實體層三元組保存更豐富也更珍貴的資訊」。

（三）Schema 品質。 拿歸納出的概念去做實體分類、事件分類、關係分類三種任務，測它能召回多少既有型別。用兩個語意層指標（BS-R、BS-C，附錄才有定義）。結果多在 80–90% 以上，並且模型越大越好。

（四）下游多跳問答。 在 MuSiQue、2Wiki、HotpotQA 上與各種檢索方法比較。值得注意的是它自己的表格顯示，Entity-KG、Entity-Event-KG、Full-KG 三種配置的差異很小（HippoRAG2 配置下 MuSiQue 的 F1 分別是 47.2、47.3、47.3），與第（二）項那個「事件遠優於實體」的鮮明對比不一致。論文沒有解釋這個落差。

7. 發現的問題與限制

論文自承的：多跳問答上它的完整版本並沒有全面勝過 HippoRAG2（表 5 裡互有勝負）；建構成本極高。

我讀出來的：

  • 92% 的 schema 對齊率不能望文生義。 那是在 FB15kET、YAGO43kET、wikiHow 這些既有資料集上做型別分類任務的召回率，衡量的是「歸納出的概念能不能涵蓋既有型別」，不是「歸納出的 schema 跟專家設計的 schema 一樣好」。一個把所有東西都標上大量寬泛概念的系統也能拿高召回。
  • 第（二）項與第（四）項的結論互相拉扯。 若事件節點真的把資訊保存從 70% 拉到 93%，下游問答不該幾乎沒有差別。合理的解釋是多跳問答的瓶頸在檢索而不在知識表示，但論文沒有討論。
  • 三元組正確率是 LLM 評 LLM。 見上。
  • 不做任何實體消歧與跨文件融合。 9 億個節點裡有多少是同一個實體的不同寫法，論文完全沒有交代。這對「web-scale 檢索」也許無所謂，對我們是核心問題。
  • 「不要把代名詞當實體」這條話術規則，在口語語料上會毀掉大部分資訊。

8. 對 extract_ohistory 的啟示

最該帶走的一件事：事件節點的價值有了量化證據。

CLAUDE.md 的硬約束 3 說「生命過程是時序化的事件序列」。AutoSchemaKG 的資訊保存度實驗替這個立場提供了外部數字：只保留實體與實體間的關係，原文資訊只剩約七成；把事件當節點，可以保到九成以上。 這正好說明為什麼把口述歷史壓成「人—述詞—人」的三元組會流失大量內容，也支持我們不走純三元組。

可借用的四件事

  1. 三階段分開抽：實體—實體、實體—事件、事件—事件。 目前 triple_exp.py 與 triple_free_exp.py 都只做一件事——從句子抽出一組主詞述詞受詞。若加一個「事件—事件」的階段，專門問時序與因果，就直接對上生命過程的需求。他們的五種關係型別（before、after、at the same time、because、as a result）幾乎可以照用，中文對應「之前、之後、同時、因為、結果」；而口述歷史裡「退伍之後」「後來」「那時候」這類相對時間表述，正是這五種關係的語言標記。
  2. 事件定義成「一個獨立的簡單句子」。 這是一個很務實的設計：不強迫事件變成結構化框架（觸發詞＋角色化論元），就讓它是一句話，靠事件之間的關係承載結構。對我們的好處是，這種事件節點天然保留原文措辭，出處也好掛——一個事件節點對回一句原文、一個時間碼。
  3. 概念化（多層抽象詞）可以取代手寫動詞表。 對每個抽出的述詞生成三個不同抽象層次的詞（「participated in」→「engage in」「attend」「involve in」），再看這些概念詞怎麼聚成類。這正是 _卡點對照表.md 第一節說的第三條路：先不限動詞地抽，再從抽出來的東西歸納出動詞表，然後拿它跟 life_nodes.py 手寫的那份比對。兩份的差異本身就是可報告的結果，而且能回答「手寫動詞表是不是偷渡了人工知識」這個懸而未決的問題。
  4. 實體概念化時餵進鄰居脈絡。 判斷一個名字是人、是機構還是作品時，把圖上鄰居的資訊一起給。我們的語料裡作品名辨識只有 1.1%，而作品名往往出現在「唱」「錄」「寫」這類述詞的受詞位置——鄰居脈絡正是這個訊號。

該避免的三件事

  1. 「不要把代名詞當實體」這條規則絕對不能照抄。 CLAUDE.md 硬約束 3 明文保護人物指代。代名詞在書面百科裡是雜訊，在口述歷史裡是把事件接成序列的接續資訊。這是本專案與這篇論文語料性質差異最大的一點。
  2. 不要用 LLM 當裁判算正確率。 紅線第 2 條。它那些 90% 以上的數字全是 DeepSeek-V3 判的。
  3. 不要指望它處理跨來源的同一實體。 它完全不做消歧，靠規模淹過去。我們的 102 位受訪者、314 份逐字稿沒有這種規模可以淹。

與四條紅線的相容性：紅線 1 相容（不用人工標注）；紅線 2 直接衝突（核心正確率指標是 LLM 評 LLM）；紅線 3 不相容（無三元組層出處，需自建）；紅線 4 部分相容（中間產物序列化成 JSON，但沒有可追溯的決策紀錄）。

與 _卡點對照表.md 的對應：第一節（動詞表該不該手寫）與第六節（相對時間與生命過程的時序）。它是這兩節的主要依據。
